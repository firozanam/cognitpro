# CognitPro Architecture

CognitPro is an AI prompt marketplace: sellers list prompts, buyers purchase
them with Stripe, and the platform keeps a commission. This document
describes what actually ships in the repository — it is the companion to the
README and the source of truth for operational behavior.

## Stack

| Layer      | Technology |
|------------|------------|
| Backend    | Laravel 12 (PHP 8.2+), modular monolith |
| Frontend   | Inertia v2 + React 19 + TypeScript, Tailwind CSS v4 (OKLCH design tokens), shadcn-style components |
| Auth       | Laravel Fortify — session-based web auth (login, registration, email verification, password reset, two-factor) |
| Payments   | Stripe via `stripe/stripe-php` (Checkout) |
| Database   | SQLite by default; MySQL/Postgres supported by Laravel's ORM layer |
| Queue      | `database` driver (a worker is required in production) |
| Tests      | PHPUnit (Feature + Unit) on SQLite `:memory:` |
| Rendering  | Client-side rendering (SSR is disabled — see [Rendering](#rendering)) |

There is **no REST/JSON API layer and no Sanctum**: every route is a `web`
route returning an Inertia response. Typed route helpers are generated by
`@laravel/vite-plugin-wayfinder` into `resources/js/routes/` — regenerate,
never hand-edit.

## Module map

Six modules under `app/Modules/`, each with a
`Providers/*ModuleServiceProvider.php` that loads its own `routes.php`.
Dependencies point toward Core only.

| Module    | Responsibility |
|-----------|----------------|
| **Core**  | Home, dashboard (buyer/seller stats), appearance |
| **Auth**  | Fortify wiring (`CreateNewUser`, `ResetUserPassword`, Inertia view bindings) |
| **User**  | Settings (profile / password / two-factor), `User` + `UserProfile` models |
| **Prompt**| Marketplace domain: prompts, categories, tags, cart, purchases, reviews |
| **Payment**| Stripe PaymentIntent payments + webhook |
| **Admin** | Moderation (approve/reject/feature), user management (ban) |

`routes/web.php` is intentionally empty — all real routes live in module
`routes.php` files. `routes/console.php` registers the scheduler.

Layering inside modules follows **Controllers → Services → Repositories →
Models**. The User and Prompt modules bind repositories to contracts
(`PromptRepositoryInterface`, `UserRepositoryInterface`, …) through their
service providers.

## Domain model

- **Users** have a single `role` column: `admin`, `seller`, or `buyer`
  (helpers `isAdmin()` / `isSeller()` / `isBuyer()` on
  `App\Modules\User\Models\User`; admins pass both seller and buyer checks).
  `banned_at` drives moderation — banned users are blocked by the
  `EnsureUserNotBanned` middleware and at Fortify login. Users implement
  `MustVerifyEmail`.
- **Prompts** belong to a seller and a category, carry tags, one of three
  pricing models (`fixed`, `pay_what_you_want`, `free`), and an appended
  `avatar` accessor on User feeds the UI.
- **Purchases** are unique per (buyer, prompt). Status lifecycle:
  `pending → completed`, with `failed` (expired/webhook mismatch),
  `refunded`, and `disputed` as terminal/exceptional states.

### Prompt moderation lifecycle

```
draft ──submit──▶ pending ──approve──▶ approved (visible on marketplace)
                      └────reject────▶ rejected (reason stored, seller notified)
```

- Only `approved` prompts appear on the marketplace.
- Sellers submit drafts; admins approve/reject from `/admin/prompts` and can
  toggle the `featured` flag.
- Rejections store a `rejection_reason` and notify the seller
  (`PromptRejectedNotification`); approvals notify via
  `PromptApprovedNotification`.

## Purchase and payment flow

1. **Initiate** — `POST /purchase/{prompt}` (or cart checkout for fixed-price
   prompts) calls `PurchaseService::initiatePurchase`, which computes the
   charge server-side. Free prompts complete immediately.
2. **Platform fee** — `PurchaseService::PLATFORM_FEE_PERCENTAGE = 15`. Of
   every completed purchase, 15% is `platform_fee` and the remainder is
   `seller_earnings` (credited to the seller's profile). The checkout page
   displays the same rate via the `platform_fee_rate` prop — there is no
   client-side fee constant.
3. **Stripe payment** — paid purchases redirect to
   `/purchases/{purchase}/stripe-payment`, which creates a PaymentIntent
   bound to the purchase (metadata + amount) and renders a Stripe Payment
   Element with its client secret.
4. **Webhook** — `POST /stripe/webhook` verifies the signature against
   `STRIPE_WEBHOOK_SECRET`, then completes the purchase idempotently on
   `payment_intent.succeeded` and marks it failed on
   `payment_intent.payment_failed` (the purchase is bound through Stripe
   metadata). Duplicate deliveries are ignored.
5. **Notifications** — buyer confirmation and seller sale alerts (queued).
6. **Expiry** — the `purchases:expire-stale` scheduled command fails
   pending purchases older than 24 hours so abandoned checkouts don't block
   a retry (the buyer/prompt pair is unique).

### Stripe setup

```
STRIPE_KEY=pk_...
STRIPE_SECRET=sk_...
STRIPE_WEBHOOK_SECRET=whsec_...
```

Point a webhook at `https://your-host/stripe/webhook` subscribing at
minimum to `payment_intent.succeeded` and
`payment_intent.payment_failed` (locally: `stripe listen
--forward-to localhost:8000/stripe/webhook`).

## Cart

Fixed-price prompts can be added to a per-user cart
(`POST /cart/add/{prompt}`) and checked out together; free items complete
immediately and paid items redirect to payment. Pay-what-you-want prompts
are purchased directly from the prompt page (the cart cannot collect a
custom price).

## Rendering

Inertia SSR is **disabled** (`config/inertia.php` → `ssr.enabled = false`):
no SSR bundle is built or served, and the app ships as client-side
rendering. To enable later: `npm run build:ssr`, serve
`bootstrap/ssr/ssr.mjs` on the configured URL, flip the flag.

## Security posture

- Security headers on every web response: `X-Content-Type-Options`,
  `X-Frame-Options: SAMEORIGIN`, `Referrer-Policy`, plus HSTS on secure
  requests (`App\Http\Middleware\SetSecurityHeaders`).
- `.env.example` ships `APP_DEBUG=false`; `composer setup` flips it to
  `true` for local development only. Set `SESSION_SECURE_COOKIE=true` on
  any HTTPS deployment.
- Admin routes sit behind the `admin` middleware alias;
  `PromptPolicy` guards prompt ownership.
- The demo seeder **refuses to run in production** — its credentials exist
  only for local development and the test suite (see below).

## Local development

```bash
composer setup        # install, .env, key, migrate, npm install + build
composer dev          # Laravel server + queue:listen + pail + Vite
```

`composer setup` seeds nothing by default. To load the demo dataset:

```bash
php artisan db:seed            # appends
php artisan migrate:fresh --seed   # clean slate
```

Seeder accounts (local/testing only, override via env):

| Account | Email | Password env | Default |
|---------|-------|--------------|---------|
| Admin   | `admin@cognitpro.com` | `SEED_ADMIN_PASSWORD` | `password` |
| Seller  | `seller@test.com` | `SEED_SELLER_PASSWORD` | `password` |
| Buyer   | `buyer@test.com` | `SEED_BUYER_PASSWORD` | `password` |

## Testing

```bash
composer test   # config:clear + pint --test + phpunit
vendor/bin/phpunit --filter=CartTest
```

PHPUnit runs on SQLite `:memory:` with the array cache/session/mail drivers
and a sync queue. Feature suites cover Admin, Cart, Payment, Dashboard,
Auth, Settings; unit suites cover the money-path services, moderation, and
notifications. Frontend gates: `npm run types`, `npm run lint`,
`npm run format:check`.

CI (GitHub Actions): `lint.yml` runs Pint/ESLint/Prettier/tsc in check
mode; `tests.yml` builds the frontend and runs PHPUnit on a PHP 8.4/8.5
matrix. There is no deploy pipeline in this repository.

## Operations runbook

### Queue worker (required)

All four notifications are `ShouldQueue` with `QUEUE_CONNECTION=database`.
Without a worker, transactional email piles up in the `jobs` table. Run and
supervise:

```bash
php artisan queue:work --tries=3 --backoff=5
```

(e.g. via supervisor/systemd; `composer dev` includes `queue:listen` for
local use.)

### Scheduler (required)

`routes/console.php` schedules `purchases:expire-stale` daily. Add to cron:

```
* * * * * cd /path-to-app && php artisan schedule:run >> /dev/null 2>&1
```

### Deployment checklist

1. `composer install --no-dev --optimize-autoloader`
2. `npm ci && npm run build`
3. `php artisan migrate --force`
4. Set `APP_ENV=production`, `APP_DEBUG=false`, `SESSION_SECURE_COOKIE=true`
5. Ensure the queue worker and scheduler above are running
6. Health check: `GET /up`

There is no Dockerfile or deploy script in this repository — deployment is
a standard Laravel manual/Forge-style flow using the checklist above.

### Backups and monitoring

Nothing automated ships here. At minimum: schedule
`php artisan db:backup`-style dumps (or filesystem snapshots of
`database/database.sqlite`) off-site, watch `storage/logs/laravel.log` and
the `failed_jobs` table, and alert on webhook signature failures in the log.

## Repository layout notes

- `resources/js/pages/` mirrors the modules (`admin/`, `auth/`, `cart/`,
  `marketplace/`, `prompts/`, `purchases/`, `seller/`, `settings/`).
- Shared frontend domain types live in `resources/js/types/prompt.ts`;
  formatting helpers in `resources/js/lib/format.ts`.
- Theme colors come exclusively from the tokens in `resources/css/app.css`
  (Tailwind v4 `@theme`, light + dark) — never hardcode palette colors.
- `docs/CODEBASE_COMPLETENESS_REPORT.md` (git-ignored) is the internal
  audit this architecture grew out of.
